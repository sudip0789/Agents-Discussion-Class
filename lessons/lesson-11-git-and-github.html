Lesson 11 · Part 2: Build

Save and share: Git vs GitHub

Hands-on

Goal: put your agent online privately, without your secrets.

Everything you built today lives in one folder on your laptop, and nothing has recorded how it got there. Git fixes that: it saves snapshots of the folder, each with a short message. In this lesson you check what Git must never save, make your first snapshot, and then put a copy online where only you can see it.

What Git will never see

  1. Open .gitignore. It came with the starter project:
    .gitignore
    # Your API token. Never commit it.
.env
# Personal Claude Code settings and system files.
.claude/settings.local.json
.DS_Store
__pycache__/
    Git doesn’t track any file listed here. Because .env is listed, your CourtListener token will never be saved in a snapshot. In the Explorer, it appears greyed out.
  2. Think about what else would belong here in practice. Your cases/ and output/ folders hold public opinions and your briefs of them, so saving them is fine. A client’s documents, or a memo about a client’s matter, would not be. Confidential files belong in .gitignore from day one, before the first snapshot.

Make your first commit

This time you type the Git commands yourself instead of asking the agent. They’re the same commands the agent would run, so this is also how you learn to read them before you approve them.

  1. Open the terminal. Choose View › Terminal. It opens in your project folder. Type each command below and press Enter. The commands are the same on Mac and Windows.
  2. Turn the folder into a Git repository. The folder you downloaded is ordinary files; Git isn’t watching it yet.
    Terminal
    git init

    Git replies “Initialized empty Git repository.” It has created a hidden .git folder, where every snapshot will be kept. Run this once per project, never again.

  3. See what Git sees.
    Terminal
    git status

    Git lists every file under Untracked files, in red: .claude/, .env.example, .gitignore, CLAUDE.md, cases/, lookup.py, output/. .env isn’t there, because .gitignore hides it from Git.

    Tip

    If the terminal says git: command not found (or “not recognized” on Windows), Git isn’t installed. Install it from git-scm.com/downloads, close and reopen VS Code, and start again from git init.

  4. Tell Git who you are. Only the first time on this computer. Use your own name, and the email address on your GitHub account.
    Terminal · first time only
    git config --global user.name "Your Name"
git config --global user.email "you@example.com"

    Every commit is signed with this name and email. If you skip this step, Git stops at the commit and replies “Please tell me who you are.”

  5. Stage the files. Staging chooses what goes into the next snapshot. The dot means “everything in this folder that isn’t ignored.”
    Terminal
    git add .
git status

    The same files now appear in green under Changes to be committed. Read the list before you go on. If .env or anything confidential were there, this is the moment to stop.

  6. Commit. A commit is a saved snapshot of everything you staged, with a message saying what changed.
    Terminal
    git commit -m "Legal research agent: briefer, checker, /brief, CourtListener"

    -m stands for message. Git replies with a short summary: how many files changed, and a line for each new file.

  7. Read the history.
    Terminal
    git log --oneline

    One line per commit, newest first. For now there’s only yours. The code at the start of the line, such as 3f9c2ab, is the commit’s ID. Git also calls your newest commit HEAD.

  8. Look inside your commit.
    Terminal
    git show --stat HEAD

    This lists every file the commit saved and how many lines each one added. Check that .env is not in the list. If the output fills the screen and ends with a :, Git is showing it one page at a time: press Space to scroll and q to quit.

  9. Read a diff. A diff shows exactly which lines changed.
    Terminal
    git show HEAD -- .claude/agents/brief-checker.md

    Added lines start with + and removed lines with -. In a first commit everything is new, so every line starts with +. The same view, in color, is in the Source Control panel (Ctrl + Shift + G): in the Graph section, click your commit, then click a file. From now on, every commit shows exactly what changed, which is how you check what an agent actually did instead of trusting its summary.

More Git commands, and the ones to be careful with

You don’t need these today. They’re the commands you’ll meet next, including in the approval requests an agent sends you. Words in angle brackets are placeholders: replace <file> with a file name and <commit> with a commit ID from git log --oneline.

Looking: safe, they change nothing

CommandWhat it shows
git statusWhat’s changed, what’s staged, and what Git isn’t tracking yet
git diffChanges you haven’t staged yet, line by line
git diff --stagedChanges you’ve staged, which will go into the next commit
git log --onelineThe history, one line per commit
git log -p <file>Every change ever made to one file, oldest at the bottom: the redline history of an agent’s instructions
git show <commit>One commit: its message and its diff
git blame <file>For each line of a file, the commit that last changed it

Saving

CommandWhat it does
git add <file>Stages one file. Safer than git add . when you only meant to save one change
git add .Stages everything in the folder that isn’t ignored
git commit -m "message"Saves the staged changes as a commit
git commit --amend -m "message"Replaces your last commit with a corrected one. Only before you’ve pushed it

Undoing

CommandWhat it does
git restore --staged <file>Unstages a file. Your edits stay in the file
git restore <file>Throws away your unsaved edits to a file and goes back to the last commit. The edits are gone for good
git restore --source=<commit> <file>Brings back a file as it was in an earlier commit, for example an agent file before a bad edit
git revert <commit>Makes a new commit that undoes an earlier one. The history keeps both, which is why it’s the safe way to undo something already shared
git rm --cached <file>Stops tracking a file without deleting it. Use it after adding a file to .gitignore that was already committed

Branches: try something without touching your working version

CommandWhat it does
git branchLists branches; a star marks the one you’re on
git switch -c <name>Creates a new branch and moves to it, for example to try a stricter checker
git switch <name>Moves to an existing branch; your files change to match it
git merge <name>Brings another branch’s commits into the one you’re on

Working with GitHub

CommandWhat it does
git initTurns a folder into a Git repository (what you did above). Once per project
git clone <url>Copies a repository from GitHub, with its whole history, onto your computer
git remote -vShows which online repositories this folder is linked to
git remote add origin <url>Links this folder to an online repository. VS Code’s Publish button does this for you
git pushUploads your new commits to GitHub
git pullDownloads new commits from GitHub and merges them into your folder

Watch out

Some commands destroy work or rewrite history, and none of them asks “are you sure?” Never approve one from an agent unless you know exactly why it’s needed.

  • git reset --hard: throws away every uncommitted change in the folder.
  • git clean -fd: deletes every untracked file, including new briefs you haven’t committed.
  • git push --force: overwrites the history on GitHub, including other people’s commits.
  • git checkout . or git restore .: throws away all unsaved edits in the folder.

Publish to GitHub, privately

Git is the tool you just used to record your history, entirely on your laptop. GitHub is a website that keeps a copy online. Pushing sends your commits there. First you make an empty repository on GitHub to receive them.

  1. Create an empty private repository. Go to github.com/new and sign in. Name it legal-research-agent and choose Private: only you, and anyone you invite, can see it. Leave Add a README, .gitignore and license off, so the repository starts empty. Click Create repository.

    Watch out

    If you tick “Add a README,” GitHub makes a commit your laptop doesn’t have, and your first push is rejected. Start empty.

  2. Copy its address. The next page shows a Quick setup box. Make sure HTTPS is selected and copy the address. It looks like https://github.com/your-name/legal-research-agent.git.
  3. Link your folder to it. Back in the VS Code terminal, paste your own address in place of the example:
    Terminal
    git remote add origin https://github.com/your-name/legal-research-agent.git
git remote -v

    A remote is a saved link to an online copy; origin is the usual name for the main one. git remote -v shows the link, twice: once for fetching and once for pushing.

  4. Name your branch main. Depending on how Git was installed, your first branch may be called master. GitHub expects main.
    Terminal
    git branch -M main
  5. Push.
    Terminal
    git push -u origin main

    The first time, GitHub asks who you are. VS Code usually shows a pop-up or opens your browser: sign in to GitHub and approve. -u remembers where to push, so from now on a plain git push is enough.

    Watch out

    If the terminal asks for a password, your GitHub password won’t work: GitHub stopped accepting passwords for Git in 2021. Press Ctrl + C to cancel and use the bonus tip below instead, which signs you in through VS Code.

  6. Check it on GitHub. Refresh the repository page. Check that it’s marked Private next to its name, that your files and commit message are there, and that .env is not in the file list.

Bonus tip: the one-click way

Steps 1 to 5 can also be done without typing a command. In a project that isn’t on GitHub yet, open the Source Control panel and click Publish Branch (or run Publish to GitHub from the Command Palette), then choose Publish to GitHub private repository. VS Code signs you in, creates the repository, adds the remote and pushes, all at once. After that, the Sync Changes button pushes new commits. Two other shortcuts do the same job:

  • GitHub CLI, a free command-line tool from GitHub (cli.github.com). After a one-time gh auth login, one command creates the repository and pushes: gh repo create legal-research-agent --private --source=. --push
  • Ask Claude Code: “Publish this project to a new private GitHub repository.” It runs the same commands you just typed, so read each one before you approve it, and check that it says private.

Knowing the commands is what lets you check what a button, or an agent, did on your behalf.

Tip

Claude Code has its own undo: press Esc twice on an empty prompt, or type /rewind, to go back to an earlier point in the conversation and restore files. It’s a quick undo inside a session, and it doesn’t track changes made by Bash commands. Git is the permanent record.

If a secret ever gets committed

Deleting a file and committing again does not remove it from Git. Every earlier snapshot still contains it, and anyone with a copy of the repository has those snapshots. If your token lands in a commit, especially one you’ve pushed:

  1. Revoke or replace the key first. Do this in the service that issued it (for this class, your CourtListener account). Once the old key stops working, a leaked copy is useless. Cleaning the history comes second, because you can never be sure nobody copied it in the meantime.
  2. Then clean the history, if you need to. Rewriting Git history is fiddly, and on GitHub it can involve cached views and copies other people made. Follow GitHub’s guide, or ask for help.
  3. Prevent a repeat: add the file to .gitignore, and read the list of changed files before every commit.

A private repo lowers the risk but doesn’t remove it: collaborators can see everything, and a repo can be made public later with its whole history.
