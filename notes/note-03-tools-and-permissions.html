Concept note N3

Tools and permissions

In one line: tools decide what an agent can do; permissions decide whether it has to ask first.

A model on its own can only write text. Tools let it act: open files, change them, run programs, search the web. Every tool you hand an agent is a new power and a new way for things to go wrong. Permissions are how you supervise those powers, the way a partner decides what a new associate can sign without checking in.

Four layers of control

In Claude Code, four separate settings shape what an agent can do. They stack: an action has to get past every layer.

LayerWhat it controlsWhere you set itIn your project
Tools lineWhich tools a subagent has at allThe tools: line in an agent filebrief-checker gets only Read, Glob, WebSearch, WebFetch: no Write, no Edit

A subagent with no tools: line doesn’t get “no tools.” It inherits every tool available to subagents, including Bash. That is why both of your agent files list their tools explicitly.

Permission modes in Claude Code

The permission mode sets the baseline: what Claude Code may do without stopping to ask you. You can change it at any time during a session.

ModeWhat runs without askingUse it when
ManualReading files only. It asks before editing files, running commands or reaching the network.While you’re learning, and for sensitive work. This is the mode for class.
Edit automaticallyReads, file edits, and common file commands like mkdir, mv and cp inside your project. Still asks before other commands.You’re reviewing the changes as they happen and trust the task.
PlanReads and explores, but doesn’t change your files. It proposes a plan and waits for your approval.Before a big change, to see what it would do first.
AutoAlmost everything. Instead of asking you, a second model (a “classifier”) checks actions like commands and web requests against your request.Long tasks once you know what you’re doing. Fewer prompts doesn’t mean safer.
Bypass permissionsEverything, with a few built-in exceptions. No prompts.Only inside an isolated container or virtual machine. Never on your own laptop.

Source: Choose a permission mode, Claude Code docs. In settings files, Manual is written default and Edit automatically is acceptEdits.

How to switch modes

  • In the terminal: press Shift + Tab to cycle through the modes. The status line shows the current one, for example “⏸ manual mode on.”
  • In VS Code: click the mode indicator under the prompt box and choose a mode.
  • Bypass permissions appears in the cycle only if the session was started with a special flag or setting.

Watch out

Newer versions of Claude Code start in Auto mode. Check the mode indicator every time you open a session, and switch to Manual while you’re learning, so you see and approve each edit and command.

Permission rules

Modes are broad. Permission rules are precise: they name a tool and, optionally, a path, command or website. There are three kinds:

  • Allow: use this without asking.
  • Ask: always ask me first, whatever the mode.
  • Deny: never do this. A deny rule applies in every mode, including Bypass permissions.

Rules live in settings files. The one you’ll use is the project file, which you commit so the rules travel with the project:

FileApplies to
.claude/settings.jsonThis project, for everyone who uses it (committed to Git)
.claude/settings.local.jsonThis project, just you (not committed)
~/.claude/settings.jsonAll your projects on this computer

Your project’s rules

This is the file you add in lesson 9. It blocks the agent from editing its own instructions and from reading your API token:

.claude/settings.json
{
  "permissions": {
    "deny": [
      "Edit(./.claude/**)",
      "Read(./.env)"
    ]
  }
}

More examples

For reference only; this isn’t a file you need for class. It shows all three kinds of rule together:

Example
{
  "permissions": {
    "allow": [
      "WebFetch(domain:courtlistener.com)",
      "WebFetch(domain:*.courtlistener.com)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Edit(./.claude/**)",
      "Read(./.env)"
    ]
  }
}
RuleMatches
Read(./.env)Reading the .env file in the current folder
Edit(./.claude/**)Changing anything inside .claude/, at any depth (** means “any folders below”)
WebFetch(domain:courtlistener.com)Opening pages on courtlistener.com only
WebFetch(domain:*.courtlistener.com)Opening pages on any subdomain, such as www.courtlistener.com or storage.courtlistener.com, but not courtlistener.com itself
Bash(git push *)Any command that starts with git push
WebSearchA bare tool name matches every use of that tool

Notice the WebFetch pair. WebFetch(domain:courtlistener.com) matches courtlistener.com and nothing else. To cover subdomains like www.courtlistener.com as well, you need the second rule with *. in front.

How a request is decided

Every time Claude wants to use a tool, Claude Code checks the rules in a fixed order: deny, then ask, then allow. The first match decides. If nothing matches, the permission mode decides.

Why it matters

Rules are enforced by Claude Code, not by the model. “Never read .env” in CLAUDE.md is a request the model weighs; "deny": ["Read(./.env)"] is a lock the software enforces, no matter what a document or a clever prompt says.

Where a path starts from

File rules use a pattern syntax borrowed from Git. The beginning of the path decides where it is anchored, and the difference between one slash and two matters:

PatternStarts fromExample
./path or pathThe current folderRead(./.env)
/pathThe settings file’s location: the project root for project settings, not the top of your hard driveEdit(/src/**)
~/pathYour home folderRead(~/notes.txt)
//pathThe very top of the file system (an absolute path)Read(//tmp/notes.txt)

Source: Configure permissions, Claude Code docs.

Watch out

Bash can do almost anything any other tool can. Claude Code applies your Read and Edit deny rules to the file commands it recognizes in Bash, such as cat, head, tail and sed, and to redirects like > file. It does not apply them to programs that open files themselves, like a Python script, or to a search like grep -r across a whole folder. (That’s also how lookup.py, a program you run, can read your token from .env while the agent’s Read tool can’t.) Real operating-system blocking needs the sandbox. Keep command prompts on, and read each command before approving it.

Codex works differently

OpenAI’s Codex, which also runs in VS Code, takes a different approach. Instead of starting from a list of tools per agent, it puts commands inside a sandbox, a boundary enforced by the operating system, and then lets you choose how often it asks before crossing that boundary.

Sandbox levels

SandboxWhat the agent can do
read-onlyInspect files, but not edit them or run commands without approval
workspace-write (default)Read files, edit inside your project folder, and run routine local commands inside that boundary
danger-full-accessNo sandbox: the file and network boundaries are removed

Source: Sandbox, Codex docs.

“Excessive agency”: the security name for this problem

The OWASP GenAI Security Project, which publishes the standard list of risks for AI applications, calls this risk Excessive Agency (LLM06:2025): an AI system that can take harmful actions in response to output that is unexpected, unclear or manipulated. It names three root causes. Each one maps to a control on this page:

Root causeWhat it meansYour control
Excessive functionalityThe agent has tools it doesn’t needA short tools: line
Excessive permissionsIts tools reach more than they shouldDeny rules for .env and .claude/
Excessive autonomyIt acts without a human checkManual mode and approving the plan

Source: LLM06:2025 Excessive Agency, OWASP GenAI Security Project.

The legal parallel is the principle of least privilege you already see in practice: a paralegal gets access to the matters they work on, not the whole document system. Give each agent the smallest set of tools and the narrowest reach that lets it do its job.

When settings files disagree, and how to see your rules

Several settings files can apply at once. When they conflict, the more specific or more authoritative one wins, in this order:

  1. Managed settings set by an organization (for example, a firm’s IT department)
  2. Options typed on the command line when Claude Code starts
  3. .claude/settings.local.json (this project, just you)
  4. .claude/settings.json (this project, shared)
  5. ~/.claude/settings.json (all your projects)

A deny rule in any of them still blocks the action, because deny is checked before allow everywhere.

To see every rule currently in force and which file it came from, type /permissions in Claude Code. When you approve an action with “Yes, and don’t ask again,” Claude Code adds an allow rule for you; /permissions is where you can review and remove those.
