Concept note N6

Git and GitHub

In one line: Git records every version of your project on your computer; GitHub keeps a copy online so you can share it.

Think of Git as a redline history for a whole folder. Every time you commit, it saves a snapshot with a note about what changed and why. When an agent edits your files, that history is how you see exactly what it did, and how you get back to a version that worked.

Git vs GitHub

Git

The tool. It runs on your computer and works entirely offline. It keeps the history in a hidden .git folder inside your project.

Legal analogy: the version history of a document, kept in your own files.

GitHub

One website that stores Git projects online, so you can back them up, share them, and review each other’s changes. GitLab and Bitbucket are others.

Legal analogy: a shared document system where colleagues can see the file and propose edits.

You can use Git without GitHub. You can’t really use GitHub without Git: it stores Git histories.

How a change travels

Git has three places a change can be. You edit files in your working folder, choose which changes go into the next snapshot (staging), and then commit. Pushing copies your commits to GitHub; pulling brings down commits made elsewhere.

Your commits are a research log

In lesson 11 you save your finished agent as your first commit. After that, each commit records one change with a short message: a new brief, or a rule you changed in an agent. Read in order, those messages tell the story of the project, and each one is a version you can open, compare or return to.

Tip

Write commit messages for a reader six months from now: what changed and why, in a few words. “Tightened a checker rule” beats “update.” After class, commit after each brief and your history becomes a dated research log.

Watch out

Never commit secrets or personal files. Once committed, a file stays in the history even after you delete it, and pushing to GitHub copies that history online. If a key gets committed, revoke it and make a new one. That’s why .env (your token) is in .gitignore from the start.

Keeping secrets out of history, and what to do if one gets in

What .gitignore does and doesn’t do

Your starter project’s .gitignore lists your token file, plus a few personal and system files:

.gitignore
# Your API token. Never commit it.
.env
# Personal Claude Code settings and system files.
.claude/settings.local.json
.DS_Store
__pycache__/
  • It does stop Git from ever staging or committing those files, so they never reach GitHub.
  • It doesn’t remove a file that was already committed. Git keeps tracking it until you remove it from the repository, and the old versions stay in history.
  • It doesn’t hide the file from the agent. Keeping an agent away from .env is a job for permission rules (see N3).

If a secret gets committed

  1. Revoke the key first. For CourtListener, generate a new token in your account and update .env. Assume the old one is compromised the moment it was pushed.
  2. Then clean up. Removing a file from history takes special tools and rewrites every later commit. GitHub’s guide below walks through it; ask for help if the repo is shared.
  3. Add the file to .gitignore so it can’t happen again.

Private isn’t the same as secret

A private GitHub repo is visible only to you and the people you invite. That’s the right setting for this project. But anyone you add later can read the full history, so secrets still don’t belong in it.
