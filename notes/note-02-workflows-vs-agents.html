Concept note N2

Workflows vs agents

In one line: a workflow follows steps you wrote; an agent chooses its own steps. Your project uses both: a workflow on the outside, agents inside.

The question that separates a workflow from an agent is simple: who decides the next step? In a workflow, you did, in advance, when you wrote the recipe. In an agent, the model decides as it goes, based on what it finds.

Two definitions

The most widely used definitions come from Anthropic’s engineering guide Building effective agents. Both kinds of system use a model and tools; the difference is who controls the path.

Workflow

“Workflows are systems where LLMs and tools are orchestrated through predefined code paths.”

Predictable. Same steps, same order, every run.

Agent

“Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage.”

Flexible. The path depends on what the model finds along the way.

Source: Erik Schluntz and Barry Zhang, “Building effective agents,” Anthropic (Dec. 19, 2024).

The loop is the whole idea. Anthropic describes agents as “typically just LLMs using tools based on environmental feedback in a loop.” Each pass, the model gets “ground truth” from the environment (a file’s contents, a search result, an error message) and uses it to decide what to do next. Claude Code’s own documentation describes the same loop as gather context → take action → verify results, repeated until the task is done, and you can interrupt it at any point.

Your project uses both

Your legal research agent is a workflow on the outside and agents on the inside. The /brief skill fixes the order: check that the case file exists, ask three questions, show a plan, hand off to the briefer, save the brief, hand off to the checker, append the checker’s report. Inside step 3, though, the case-briefer is an agent: it decides how to read the opinion page by page, which passages to quote, and which statements are holding and which are dicta.

That split is deliberate. The parts you want to happen every time, like asking your level and running the checker, are fixed in the workflow, so the model can’t skip them. The parts that depend on the case, like which passages matter, are left to the agent.

Tip

Start with the simplest thing that works. Anthropic’s advice is to find “the simplest solution possible, and only increas[e] complexity when needed.” If a fixed checklist does the job, you don’t need an agent.

Why the checker is a separate agent

Lawyers already know this principle as separation of duties. The associate who drafted a brief shouldn’t be the only person who cite-checks it, and the person who approves a payment shouldn’t be the one who requested it. The same logic applies to agents. Three design choices make the brief-checker independent of the case-briefer:

Design choiceWhat it prevents
Fresh contextThe checker never sees the briefer’s reasoning, so it isn’t persuaded by it. It sees only the finished brief, the way a reader would, and reads the whole opinion itself.
Narrow tools (Read, Glob, WebSearch, WebFetch)It has no Write or Edit, so it can’t quietly “fix” a bad quote and hide the problem. It can only report.
A different jobIts instructions are to find problems, not to finish the brief. An agent asked to check its own work tends to confirm it.

Why it matters

A model that invented a citation will often defend it if asked in the same conversation, because the invented text is now part of its context. A checker that starts fresh, has to find the quote in the opinion, and has to open a page showing the cited case doesn’t have that problem.

Memory: subagents start blank

Each subagent starts with a fresh context window. It doesn’t remember previous runs, and it doesn’t see your conversation with the main agent. What it does get is limited and predictable:

A subagent starts withA subagent does not get
Its own instructions (the body of its agent file)Your conversation with the main agent
Your CLAUDE.md filesFiles the main agent already read
The task message the main agent writes for itAnything from previous runs, unless it’s in a file

Source: Subagents, Claude Code docs.

So anything an agent should remember has to be written to a file. In your project that means:

  • CLAUDE.md: rules for every session, written by you.
  • .claude/agents/ and .claude/skills/: the briefer’s, the checker’s and /brief’s instructions, written by you.
  • output/: every brief, in a folder per case, never overwritten.

This is also why /clear is safe to use often. It empties the conversation, but the files stay, and the next run reads them again. Your agent doesn’t learn between runs: a rerun of the same case starts from the same instructions, so the wording may differ but the holding, disposition and pinpoints shouldn’t. Memory in plain files has a bonus: you can open it, read it and correct it, the way you’d correct a file memo.

Why not make everything an agent?

Agents are impressive, so it’s tempting to use them everywhere. Anthropic’s guide is blunt that you shouldn’t: “workflows offer predictability and consistency for well-defined tasks, whereas agents are the better option when flexibility and model-driven decision-making are needed at scale.” The costs of an agent are real:

  • Errors compound. Each loop builds on the last. One wrong turn early, like a misread search result, can steer every later step.
  • It’s harder to check. A workflow takes the same path every time, so you can review the path once. An agent takes a different path every run.
  • It costs more. Every pass through the loop adds tokens to the context window, which means more time and money.
  • It has more power to misuse. An agent needs tools to act, and every tool is something that can go wrong. See N3 Tools and permissions.

The guide also lists safeguards that make agents workable: ground truth from the environment at every step, pauses for human feedback at checkpoints, and stopping conditions such as a maximum number of steps. Your project has all three: the opinion itself and the checker’s citation lookups supply ground truth, the plan approval is a checkpoint, and the workflow ends after a fixed number of steps.
